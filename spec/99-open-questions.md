## 事件查询缺少「取最新 N 条」的反向接口

**现状（限制）**

`onebox_event_query` 只按 `seq` 升序返回，翻页靠 `since_seq` 单向前向推进，
没有「从末尾取最近 N 条」的能力。

**影响**

任何想「显示最近事件」的外衣都拿不到高效实现：

- WinUI 3 外衣（`shells/windows/OneBox.Shell.WinUI/MainWindow.xaml.cs`，
  常量 `QueryLimit`）用 `limit=1000` 查询后截取末尾 50 条绕过。
- 该绕过只在事件总数 ≤ 1000 时正确；超过 1000 条后，列表展示的将不是最新的
  事件，且没有任何提示。**这是权宜之计，不是正确实现。**

**候选方案（未决）**

未来若确有需要，考虑新增：

```c
onebox_rc onebox_event_query_recent(onebox_core *handle, uint32_t limit, char **out_json);
```

待定项：返回是否仍按 `seq` 升序？是否沿用现有查询信封？是否需要与
`event_type` / `source` 过滤组合？契约冻结前，核与所有外衣一律按
「正向查询 + 外衣自行截取」处理。

**触发条件**

真实使用中事件数接近或超过 1000，或某个外衣需要可靠的「最新视图」/分页时，
正式立项解决。

## 已知架构债：终端模块绕过核

**现状**

终端模块（`crates/onebox-terminal`）目前完全绕过核：不注册为模块、不发心跳、
不写任何事件。它只是被外衣直接通过 C ABI 调用的一个独立 DLL。

**这是有意暂缓，不是疏忽。** 原因：契约 3（消息必经核）与契约 5（模块生命周期）
尚未实现，先造消费者会返工。

**触发条件**

核开始做模块生命周期时，终端是第一个纳入者。

## 已记录、暂不处理的运行时风险

以下问题已知，当前不改，记录在案：

- **`write` 在 UI 线程可能阻塞**：`onebox_terminal_write` 是 `write_all + flush`，
  若子进程不读、PTY 缓冲满会阻塞调用线程（当前是 UI 线程）。大段粘贴有冻结界面的
  风险；将来可改为写队列 + 写线程。
- **`close` 持锁 join 读线程**：`onebox_terminal_close` 在持有会话锁时等待读线程
  退出（上限 2s），在 UI 线程上可能短暂卡顿；超时后放弃 join（Arc 保证内存安全，
  仅线程短暂泄漏）。
- **终端测试与默认程序硬编码 Windows**：集成测试用 `cmd.exe`、默认程序
  `powershell.exe`，无法在 macOS/Linux 运行；客场要用需参数化。
